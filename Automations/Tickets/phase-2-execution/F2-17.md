# F2-17 Primer: Phase 2 Live-Testing Pass via Appium

**For:** New coding-agent session
**Project:** OpenHuman — Workflows & Automations
**Previous work:** F2-1..F2-16 ship the Phase 2 Rust surface end-to-end. F2-16b drops two scenario-specific WDIO specs. F2-17 is the **comprehensive live-testing pass** that walks the full Phase 2 surface through the macOS Appium harness against the real `.app` bundle.

---

## What Is This Ticket?

A single dedicated end-to-end spec that drives every Phase 2 capability through the real desktop app — chat-driven drafting, multi-node execution, every new trigger, every new node kind, soft-delete + restore, `active_hours` enforcement. The goal is the **live-testing gate** the user requires before treating Phase 2 as "really shipped" (per the [User profile](../../../.claude/projects/-Users-jad-openhuman/memory/user_profile.md) note: "gates everything through live testing").

### Why It Matters

- Rust unit tests confirm the executor + validator + store are correct in isolation.
- F2-16b's two specs cover the hero + catalog flows.
- **Neither proves the Phase 2 surface works through the actual chat-driven UI in the real app bundle.** A capability that "passes 345 unit tests but doesn't render on macOS" is a regression waiting to happen.
- F2-17 is the merge gate that says "Phase 2 is shippable to a real user, not just to CI."

## What This Ticket Must Accomplish

### Goal

One spec at `app/test/e2e/specs/workflows-phase-2-live.spec.ts` that drives the **full Phase 2 capability set** through the macOS Appium (XCUITest :4723) harness against the real `.app` bundle. The spec is structured as a single tokio-runtime session walking through scenarios sequentially so the test cost stays bounded (Appium session startup is ~30s):

1. **Multi-node chain via direct RPC** (proves the executor + persistence path)
   - `workflows_create` with a 3-node chain: `tool_call` → `agent_prompt` → `channel_message` (channel target is a deterministic mock connection).
   - `workflows_run_now` → poll `workflows_get_run` until terminal.
   - Oracle: 3 step rows persisted in walk order; final step's `output_json` carries the substituted body.

2. **Webhook trigger end-to-end** (proves F2-9 + F2-9b)
   - Register a `Trigger::Webhook` workflow via RPC.
   - POST to the tunnel URL using the spec's HTTP client (no LLM in the loop — `agent_prompt` node uses the test stub).
   - Oracle: run lands `Succeeded`; payload visible in step output.

3. **`composio_event` fan-out** (proves F2-10)
   - Register two workflows on the same `(toolkit, trigger_id)` pair.
   - Drive `dispatch_matching_workflows` via direct RPC simulating the bus event.
   - Oracle: both workflows produce runs.

4. **`channel_message` filter** (proves F2-11)
   - Register a workflow with `Trigger::ChannelMessage { provider: "slack", filter: { contains: "URGENT" } }`.
   - Simulate one matching + one non-matching inbound message.
   - Oracle: exactly one run.

5. **`condition` branching** (proves F2-6)
   - Workflow with `classify → condition → (alert | log)`.
   - Drive `workflows_run_now` twice with different stub-agent outputs (one routes to `alert`, the other to `log`).
   - Oracle: each run's step rows match the expected branch.

6. **Soft-delete + restore round-trip** (proves F2-14)
   - `workflows_delete` a workflow → confirm absent from default `workflows_list`.
   - `workflows_list { include_deleted: true }` → confirm present.
   - `workflows_restore` → confirm back in default list.

7. **`active_hours` gate** (proves F2-15)
   - Workflow with a cron + `active_hours` window that doesn't include `now`.
   - Drive a cron tick via the test helper (or direct executor call from outside the window).
   - Oracle: `WorkflowRunSkipped` event published with `reason: outside_active_hours`.

8. **Starter-catalog Phase 2 entries** (proves F2-12)
   - `workflows_list_starter_templates(phase=2)` → returns 9 templates including RU-5..RU-9.

9. **Capability surface** (proves F2-16's catalog work)
   - `about_app_list_capabilities` → returns the 7 Phase 2 entries (`automation.multi_node_chain`, `automation.webhook_trigger`, etc.).

### What's NOT in scope

- **Drafter LLM integration**: F2-17 uses direct RPC to seed workflows rather than chatting through the drafter. The drafter prompt is already covered by F2-13 unit tests + F2-16b's hero spec. F2-17 is about runtime — the executor + persistence + UI surface — not the chat → preview render path (which is F2-16b's job).
- **Mock-LLM harness for every scenario**: where a scenario needs agent reasoning (e.g. condition branching), use the `set_test_agent_prompt_override` test seam the Rust core already exposes, driven via a debug RPC (`workflows_dev_seed_agent_response` or similar — F2-17 adds it if missing).

## Architectural Decisions

| Decision | Reference | Summary |
|---|---|---|
| One spec, 9 scenarios | This ticket | Appium session startup is the bottleneck; one session amortises the cost. Per-scenario specs would inflate CI time 9×. |
| Direct RPC for workflow seeding | This ticket | F2-17 tests **runtime + UI surface**, not the chat-driven drafter (F2-16b's job). Skipping the LLM keeps the test deterministic + cheap. |
| Dev-only debug RPCs gated by env var | This ticket | A real user can't reach `workflows_dev_inject_agent_stub`; CI sets `OPENHUMAN_DEV_E2E=1` so the spec can. |
| Skip drafter LLM scenarios | This ticket | Drafter coverage already lives in F2-13 unit tests + F2-16b's hero spec; F2-17 doesn't duplicate. |

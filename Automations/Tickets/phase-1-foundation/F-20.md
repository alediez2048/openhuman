## What Is This Ticket?

The chat orchestrator delegates external-service tasks (Slack message, Gmail send, LinkedIn post, …) to `integrations_agent` via `delegate_to_integrations_agent { toolkit }`. That sub-agent calls `composio_execute { tool: "<SLUG>", arguments: {...} }`. Two related failure modes have caused recurring user-visible bugs:

**Bug 1 — slug hallucination.** The LLM passes `"composio"` or `"linkedin"` (toolkit names) as the `tool` argument to `composio_execute` instead of a real action slug like `"LINKEDIN_CREATE_LINKED_IN_POST"`. The backend rejects with `400 Bad Request: Toolkit "<arg>" is not enabled`. The tool's `Err` branch surfaces a free-form anyhow string. The orchestrator LLM then fabricates a plausible-sounding excuse ("LinkedIn permissions issue", "you need the w_member_social scope", "your token is invalid") — none of which is the real cause.

**Bug 2 — silent non-execution.** integrations_agent sometimes returns plain text ("here's the post I would have written…") without ever calling `composio_execute`. The user thinks the action happened; nothing did.

### Direct repro (live, 2026-05-24)

```
15:34:08  orchestrator: delegate_to_integrations_agent(skill_filter=linkedin)
15:34:09  integrations_agent: fuzzy filter narrowed toolkit=linkedin total=17 kept=4
15:34:18  backend: 400 Bad Request: Toolkit "composio" is not enabled
          ← agent passed tool: "composio" instead of LINKEDIN_CREATE_LINKED_IN_POST
15:35:58  (user re-auth'd, retried)
15:35:58  orchestrator: delegate_to_integrations_agent(skill_filter=linkedin)
15:35:58  integrations_agent: fuzzy filter narrowed toolkit=linkedin total=22 kept=5
15:36:07  delegate_to_integrations_agent success=true output_chars=688
          ← BUT ZERO composio_execute calls fired
15:36:10  orchestrator: no tool calls — returning final 387-char text to user
          ← user told "posted!" or "couldn't post for X reason"; nothing actually happened
```

Direct CLI verification confirmed `LINKEDIN_CREATE_LINKED_IN_POST` exists in Composio's LinkedIn toolkit (plus `LINKEDIN_CREATE_ARTICLE_OR_URL_SHARE`, `LINKEDIN_CREATE_COMMENT_ON_POST`, ~20 others). The chat agent's "no posting actions available" / "missing scope" claims are pure fabrication.

### Why It Matters

- This is a **trust killer.** Users follow agent advice ("update your token", "re-grant scopes") that doesn't fix anything because the agent invented the cause.
- Phase 2 multi-node chains will compound the failure: a chain whose Node 2 delegates to integrations_agent on a wrong slug fails silently and the user has no way to triage.
- F-16 fixed this for `workflow_node`. F-19 fixed it structurally for MCP tools. Composio + chat-path needs the same treatment.

## What Was Already Done

- **F-16** added `composio_list_toolkits` + `composio_list_tools` discovery tools and a workflow_node prompt section ("DO NOT explore every connected toolkit") to break the same disease on the workflow runtime path. workflow_node's `agent.toml` allowlist gets discovery first, then `composio_execute`.
- **F-19** introduced `McpToolErrorKind` enum + `classify_mcp_error` + `render_mcp_tool_error` for MCP-tool failures. The orchestrator prompt grew a "MCP tool failures — surface verbatim, never confabulate" section with 4 non-negotiable rules.
- **`composio_execute` exists** at `src/openhuman/composio/tools.rs:777` (struct `ComposioExecuteTool`) and is named in `integrations_agent/agent.toml`'s `[tools].named` list.
- **`integrations_agent/prompt.md` already says** "Never fabricate action slugs. Pull them from composio_list_tools." The LLM ignores this advice because the constraint is purely prose, with no structural enforcement.

### Audit findings (the actual code paths)

- `ComposioExecuteTool::execute` at `composio/tools.rs:839` accepts `tool` as a free-form string. Only validation is `tool.is_empty()` at line 846. Anything else (lowercase, no underscores, toolkit name, garbage) gets forwarded to the backend verbatim.
- The `Err` branch at line 1004 is `Ok(ToolResult::error(e))` — same free-form-string shape F-19 ripped out for MCP. The orchestrator gets a string, invents an explanation.
- `integrations_agent/agent.toml`'s `[tools].named` is `["composio_list_tools", "file_read", "composio_execute"]`. Missing: `composio_list_toolkits` (needed when the agent doesn't know which toolkit slug to query for tools, though for integrations_agent which is single-toolkit-scoped this is less critical than for workflow_node).

## What This Ticket Must Accomplish

### Goal

`integrations_agent → composio_execute` either succeeds or fails with a structured, verbatim-rendered error. The orchestrator can no longer fabricate plausible-sounding excuses on top of a free-form failure string. The "agent returned text without actually calling the tool" pattern is structurally discouraged via prompt + (optionally) iteration validation.

### Deliverables Checklist

#### Part 1 — Slug-shape validation in `composio_execute`

Catch the LLM hallucinating non-slug strings BEFORE the backend rejects them.

- [ ] In `composio/tools.rs::ComposioExecuteTool::execute` (after the `tool.is_empty()` check around line 846):
  - Validate `tool` matches the Composio action-slug shape: `^[A-Z][A-Z0-9]*(_[A-Z0-9]+)+$` (uppercase letter, then at least one underscore-separated segment of uppercase/digits — e.g. `GMAIL_SEND_EMAIL`, `LINKEDIN_CREATE_LINKED_IN_POST`).
  - If it doesn't match, return a structured `⚠ Composio tool error` block with `kind: invalid_slug_shape`, detail = "received `<tool>`", suggestion = "Call `composio_list_tools(toolkit='<X>')` first to get real action slugs. Slugs always look like `GMAIL_SEND_EMAIL`, `SLACK_SEND_MESSAGE`, `LINKEDIN_CREATE_LINKED_IN_POST` — uppercase + underscores, never a toolkit name like `composio` / `linkedin` / `slack`."
- [ ] Log at `warn!` with `target: "composio"`, `tool=<invalid>`, `kind=invalid_slug_shape` so triage is trivial.

#### Part 2 — Structured Composio tool errors (mirror F-19)

- [ ] In `composio/tools.rs` (or a new sibling module `composio/tool_errors.rs` for cleanliness — your call):
  - Add `pub(crate) enum ComposioToolErrorKind` with variants:
    - `InvalidSlugShape` (Part 1 above — the "LLM passed `composio` or `linkedin`" case)
    - `ToolkitNotEnabled` (backend `400: Toolkit "<X>" is not enabled` after a slug-shape-valid call where the toolkit isn't in the user's allowlist)
    - `AuthFailed` (backend / upstream 401/403 — "your token expired, reconnect")
    - `RateLimited` (backend / upstream 429)
    - `UpstreamProviderError` (backend forwarded a 4xx/5xx from Gmail/Slack/LinkedIn/etc.)
    - `ScopeBlocked` (the existing `ToolDecision::BlockedByScope` path at lines 885–895 — same shape)
    - `NotCurated` (the existing `ToolDecision::NotCurated` path at lines 897–907)
    - `ActionNotFound` (backend says the action slug doesn't exist for that toolkit)
    - `Timeout`
    - `Unknown` (catch-all — conservative, never guesses)
  - Add `label()` returning a stable snake_case string per variant (e.g. `invalid_slug_shape`, `toolkit_not_enabled`, …).
  - Add `suggestion()` returning a concrete actionable next step per variant. The orchestrator surfaces this verbatim instead of inventing remediation.
  - Add `classify_composio_error(err_string: &str) -> ComposioToolErrorKind` that pattern-matches the strings emitted by `composio/execute_dispatch.rs` and the backend into a kind. Conservative — returns `Unknown` when no pattern fires.
  - Add `render_composio_tool_error(tool: &str, kind: ComposioToolErrorKind, detail: &str) -> String` producing the F-19-shape stable block:
    ```
    ⚠ Composio tool error
    tool: LINKEDIN_CREATE_LINKED_IN_POST
    kind: toolkit_not_enabled
    detail: Backend returned 400: Toolkit "linkedin" is not enabled for this entity
    suggestion: <verbatim, per-kind>

    [Surface this block verbatim. Do NOT invent additional error details.]
    ```
- [ ] Update `ComposioExecuteTool::execute`:
  - The existing scope-block paths (lines 885–895, 897–907) and the final `Err(e) => Ok(ToolResult::error(e))` at line 1004 ALL render via `render_composio_tool_error(...)`.
- [ ] Tests: ≥7 unit tests for the kind classifier (one per non-trivial variant) + ≥2 for the renderer (stable shape + Unknown branch).

## Architectural Decisions

### Why slug-shape regex validation, not "look it up in a catalog"?

A catalog check would require an async backend call per `composio_execute` invocation just to validate the slug — adds latency. The shape regex catches >95% of LLM hallucinations (lowercase toolkit names, garbage strings) with zero network cost. The remaining edge cases (well-shaped slugs that happen to not exist) are caught by the backend's `ActionNotFound` response and surfaced via the structured error path. Best of both worlds.

### Why classify the existing scope-block paths under the same enum?

`ToolDecision::BlockedByScope` and `ToolDecision::NotCurated` already produce error messages today. Wrapping them in the same `ComposioToolErrorKind` enum gives the orchestrator one rendering contract instead of three — and lets the user's chat surface display "scope blocked by your preferences" verbatim instead of letting the LLM paraphrase it.

### Why update the orchestrator prompt instead of pre-rendering the error in markdown?

The orchestrator can already render markdown blocks verbatim — what it lacks is the discipline to do so. The prompt is the right place to encode the rule because it generalises: future tool surfaces that follow the same structured-error pattern (e.g. an HTTP tool, a webhook tool) inherit the discipline for free. Pre-rendering in markdown would just push the problem elsewhere.

### Why not also fix the "agent returns text instead of acting" bug structurally?

Detecting "you should have called a tool" reliably is an LLM-evaluation problem — needs another agent or rule engine. Cost > benefit for this ticket. Prompt-level discipline ("if asked to act, act") plus the F-20 structured errors (so failed calls don't disguise themselves) is the right scope.

If the prompt fix doesn't move the needle, a follow-up ticket can add a "no-tool-call iteration counter" that detects N consecutive iterations without tool calls and surfaces a structural error to the orchestrator.

### Why is this not a Phase 2 ticket?

Same reasoning as F-19: this is residual Phase 1 polish. The bug exists today, hits the user today, blocks trust today. Phase 2 (multi-node workflows) will compound the failure if we leave it. Better to close it now than to debug it under Phase 2's larger surface.

## Acceptance criteria

- Calling `composio_execute({ tool: "linkedin", arguments: {} })` from any agent returns a structured `⚠ Composio tool error\nkind: invalid_slug_shape\n...` block — NOT forwarded to the backend.
- Calling `composio_execute({ tool: "LINKEDIN_NONEXISTENT_ACTION", arguments: {} })` returns a structured block with `kind: action_not_found` (or `toolkit_not_enabled` / `upstream_provider_error` as appropriate) — NOT a free-form anyhow string.
- Orchestrator prompt has a single section that covers both MCP and Composio structured tool errors with the same 4 verbatim-render rules.
- integrations_agent prompt has the wrong-vs-right slug example + the "if asked to act, act" rule.
- `cargo test --lib composio::tool_errors` (or wherever the classifier lives) passes ≥9 new tests.
- Full regression sweep stays green: 202 workflows + 52 connections + 508 composio (+ new tests) + 602 memory_tree + 33 agent loader.

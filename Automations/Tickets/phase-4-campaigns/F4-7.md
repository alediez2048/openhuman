# F4-7 Primer: `for_each` Iteration Node Kind

**Project:** OpenHuman — Workflows & Automations / Phase 4 Campaigns
**Dependencies:** F4-4 (`EntityStore` trait), F4-5 + F4-6 (adapters).

---

## What Is This Ticket?

A new node kind that iterates over an `EntityStore` query result, running its inner chain once per matching record. Lets a single workflow process multiple entity records natively, instead of the agent managing the loop in-prompt.

### Why It Matters

Without `for_each`, "send an email to 20 vendors today" requires the LLM to manage the for-loop AND the rate-limiting AND the dedup — every run, from scratch. Native iteration moves that complexity into the runtime where it's deterministic and cheap.

---

## Goal

Extend `NodeKind` and `NodeConfig`:

```rust
pub enum NodeKind {
    // ... existing kinds ...
    ForEach, // NEW
}

pub enum NodeConfig {
    // ... existing variants ...
    ForEach(ForEachConfig), // NEW
}

pub struct ForEachConfig {
    /// Which entity store to iterate. Resolved against the parent campaign's
    /// `entity_binding` when the workflow is part of a campaign; required
    /// to be explicit when the workflow stands alone.
    pub entity_binding: Option<EntityRef>,
    /// Query against the entity store.
    pub query: EntityQuery,
    /// Per-iteration sub-chain — these node ids run once per matching record,
    /// with the record exposed as `{{record.*}}` in templates.
    pub body_nodes: Vec<NodeId>,
    /// Optional per-iteration delay (so e.g. "20 vendors today" spreads across
    /// the day rather than 20 sends in 5 seconds).
    pub per_iteration_delay_secs: Option<u32>,
    /// Max records to process per workflow run. Acts as a hard cap; the
    /// campaign-level throttle (F4-8) is the rate gate.
    pub max_per_run: u32,
}
```

Executor body (`src/openhuman/workflows/executor.rs::execute_for_each`):

1. Resolve `entity_binding` (campaign-inherited if `None`).
2. Open the `EntityStore` via the registry.
3. Run `store.list(query)` to fetch candidate records.
4. Apply `max_per_run` cap.
5. For each record:
   - Push a `record` context into `NodeContext.iteration_scope` so `{{record.<field>}}` templates resolve.
   - Walk the `body_nodes` chain (reuses the existing `execute_inner` walker but scoped to this iteration's subgraph).
   - On chain success: optional `update` against the entity store (status column write-back) — drafter generates this based on user intent.
   - On chain failure: respect the workflow's `on_error` policy.
6. Aggregate results into a `for_each` step output: `{ records_processed: N, records_succeeded: M, records_failed: K }`.

Templating extension: `NodeContext` gains an `iteration_scope: Option<EntityRecord>`. `{{record.email}}` resolves against `iteration_scope.fields["email"]` when inside a `for_each` body.

Validator:

- `ForEachConfig.body_nodes` must all be valid node ids in the workflow.
- `entity_binding` must be present OR the workflow must belong to a campaign with a binding.
- `max_per_run ∈ [1, 1000]`.
- `per_iteration_delay_secs ∈ [0, 3600]`.

### Tests

- 3-record entity store + 1 `for_each` node + 1 inner agent_prompt node → 3 step rows (one per record) + correct templated content.
- Failure on record 2 with `on_error: Continue` runs record 3 anyway.
- Failure on record 2 with `on_error: Halt` short-circuits.
- `max_per_run = 1` processes exactly 1 record even if query returns 10.
- `per_iteration_delay_secs = 1` inserts the delay.
- Template `{{record.email}}` resolves correctly per iteration.

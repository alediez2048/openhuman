# F4-5 Primer: Google Sheets Adapter

**Project:** OpenHuman — Workflows & Automations / Phase 4 Campaigns
**Dependencies:** F4-4 (`EntityStore` trait).

---

## What Is This Ticket?

The first concrete `EntityStore` implementation. Google Sheets is the universal floor — every Gmail user has access. Sheet columns become entity fields; rows are records; status writes go back to the sheet.

### Why It Matters

Locks the trait against a real backing store. Sheets is the test for "does our trait handle untyped, header-derived schemas." Most users don't have Attio but most have a sheet they want to drive a campaign from.

---

## Goal

`src/openhuman/campaigns/entity_store/google_sheets.rs`:

- Authenticates via the existing Composio `GOOGLESHEETS` integration (no separate OAuth dance — reuse what `/connections` already provides).
- `schema()` reads the first row of the configured `range` as column headers; field types are inferred via heuristic (email-format → `EmailAddress`, phone-format → `PhoneNumber`, ISO date → `DateTime`, etc.) with `Unknown` as fallback.
- `list(query)` reads all rows in `range`, applies `EntityFilter`s in-process (Sheets API doesn't support server-side filtering uniformly).
- `get(&id)` resolves the row by primary-field equality (typically `email`).
- `update(&id, patch)` writes back to the row's cells via the Composio `GOOGLESHEETS_UPDATE_VALUES` action.
- `subscribe()` returns a polling stream — polls the sheet every 30 seconds, emits `EntityChange` when row counts or modified-time signals new/changed rows. Push subscriptions via Drive API are a follow-up.
- Identity: `EntityId { adapter: "google_sheets", native: format!("{spreadsheet_id}:row:{row_number}") }`.

Identity caveats:
- Row number identity is fragile (insertion/deletion shifts ids). The adapter mitigates by ALSO carrying a stable `primary_field` value in the EntityRecord — callers should prefer that for cross-run matching.
- If the user adds a row above existing rows, every downstream `EntityId` shifts. Document this loud-and-clear. Recommendation in user-facing copy: "use the column header for your primary key (e.g. email) and we'll match against that, not row number."

Schema discovery output for a sheet with headers `[email, name, status, last_contacted, interest_score]`:

```json
{
  "primary_field": "email",
  "fields": [
    { "key": "email", "label": "Email", "kind": { "kind": "email_address" }, "required": true },
    { "key": "name", "label": "Name", "kind": { "kind": "string" }, "required": false },
    { "key": "status", "label": "Status", "kind": { "kind": "string" }, "required": false },
    { "key": "last_contacted", "label": "Last contacted", "kind": { "kind": "date_time" }, "required": false },
    { "key": "interest_score", "label": "Interest score", "kind": { "kind": "number" }, "required": false }
  ]
}
```

### Tests

- Schema inference from synthetic header sets (email vs phone vs date vs unknown).
- `list` with a filter returns only matching rows.
- `update` writes the correct cell — verified against a fake Composio executor.
- Polling subscription detects new rows.
- Identity collision: same `spreadsheet_id` different sheets returns different `EntityId`s.

# F4-9 Primer: Approval Queue (Draft-Mode Conversation Handler)

**Project:** OpenHuman — Workflows & Automations / Phase 4 Campaigns
**Dependencies:** F4-3 (`ApprovalPolicy::DraftAndApprove`).

---

## What Is This Ticket?

The user-facing surface for **Mode (B) Draft mode** from the 2026-05-26 grill. Outbound actions (emails, SMS, posts) in a campaign with `ApprovalPolicy::DraftAndApprove` don't fire directly — they land in an approval queue. User opens the queue, reviews each draft, edits inline if needed, taps Approve → send fires. Or taps Reject → drop without sending.

### Why It Matters

This is the MVP conversation-handling surface. Mode (B) was locked as the floor in the grill — agents can DRAFT but not SEND autonomously until proven trustworthy. Without this UI, draft mode is just "the agent sat on the draft and never told anyone."

---

## Goal

New SQLite table `approval_queue`:

```sql
CREATE TABLE IF NOT EXISTS approval_queue (
    id            TEXT PRIMARY KEY,
    campaign_id   TEXT NOT NULL REFERENCES campaigns(id) ON DELETE CASCADE,
    workflow_id   TEXT NOT NULL REFERENCES workflows(id) ON DELETE CASCADE,
    run_id        TEXT NOT NULL,
    node_id       TEXT NOT NULL,
    action_kind   TEXT NOT NULL,  -- e.g., "gmail_send", "twilio_sms"
    target        TEXT NOT NULL,  -- recipient identifier (email, phone, channel)
    payload_json  TEXT NOT NULL,  -- full action payload (subject + body for email, etc.)
    context_json  TEXT,           -- the triggering entity record + agent's rationale
    status        TEXT NOT NULL,  -- "pending" | "approved" | "rejected" | "sent" | "failed"
    created_at    TEXT NOT NULL,
    decided_at    TEXT,
    decided_by    TEXT
);
CREATE INDEX idx_approval_queue_status ON approval_queue(status);
CREATE INDEX idx_approval_queue_campaign_status ON approval_queue(campaign_id, status);
```

Migration 008 lands this.

`src/openhuman/campaigns/approval/`:
- `types.rs` — `ApprovalEntry`, `ApprovalDecision { Approve, Reject, Edit { new_payload } }`.
- `store.rs` — CRUD: `enqueue`, `list_pending`, `get`, `record_decision`, `mark_sent`, `mark_failed`.
- `ops.rs` — RPC ops + agent tools.

Executor integration:
- When a node would perform an externally-visible action (gmail_send, twilio_sms, channel_message) AND the workflow's parent campaign has `ApprovalPolicy::DraftAndApprove`, the executor:
    1. Builds the action payload as usual.
    2. Calls `approval::store::enqueue(...)` instead of executing.
    3. Returns a step output: `{ queued_for_approval: true, approval_id }`.
    4. Marks the step `Succeeded` (the draft IS the success state).
- A separate execution path triggered on `Approve` decision: re-issues the action with the (possibly edited) payload.

UI surface:
- New route `/approvals` — list of pending entries, grouped by campaign.
- Each entry card: recipient + action kind + payload preview (subject + first 200 chars of body) + Approve / Reject / Edit buttons.
- Inline edit: tap → edit → save updates `payload_json`.
- Batch operations: select multiple → approve all / reject all.
- Push notification when new drafts enqueue (uses existing notifications surface).

RPC surface:
- `openhuman.approvals_list_pending(campaign_id?)`
- `openhuman.approvals_get(id)`
- `openhuman.approvals_approve(id, edited_payload?)`
- `openhuman.approvals_reject(id, reason?)`
- `openhuman.approvals_batch_approve(ids[])`

DomainEvent variants: `ApprovalEnqueued`, `ApprovalDecided`, `ApprovalSent`, `ApprovalFailed`.

### Tests

- Workflow with `DraftAndApprove` policy → outbound action enqueues instead of executing.
- `approve(id)` re-issues the action with the original payload.
- `approve(id, edited_payload)` re-issues with the new payload.
- `reject(id)` marks the entry rejected and DOES NOT execute.
- `batch_approve` works on N entries.
- Push notification fires on `ApprovalEnqueued`.
- Pending queue is per-campaign-filterable.

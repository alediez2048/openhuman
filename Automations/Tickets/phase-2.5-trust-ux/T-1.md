# T-1 Primer: Delivery-Receipt Sub-Event

**Project:** OpenHuman — Workflows & Automations / Phase 2.5 Trust UX
**Dependencies:** Phase 2 shipped. F-16 + F-21 honesty fixes shipped (f87492cf, df170b19). None within Phase 2.5.

---

## What Is This Ticket?

When the workflow_node sub-agent calls a Composio write tool (`*_SEND_*`, `*_CREATE_*`, `*_UPDATE_*`, `*_POST_*`) and Composio reports `successful=true`, emit a structured `DeliveryReceipt` and persist it on the run step. This is the **data foundation** for T-2's per-run outcome card — without it, the UI can only render the agent's free-form narrative.

### Why It Matters

After F-21, a run that says `Succeeded` *did* call at least one tool. But the user still has no way to tell:
- *What* tool? (`SLACK_SEND_MESSAGE` vs `SLACK_LIST_CONVERSATIONS`)
- *To whom?* (recipient, channel, file id)
- *Provable link?* (message_id, deep-link URL)

`composio_execute` already has all this information in `resp.markdown_formatted` and the raw JSON envelope it returns. Today the executor swallows the structure and stores only the agent's prose summary. T-1 captures the structure.

## Goal

A new type that travels alongside the existing `ToolCallObservation` event flow:

```rust
// src/openhuman/workflows/types.rs

/// Concrete, user-renderable evidence that a workflow run produced a
/// real-world side effect (email sent, message posted, file created,
/// record updated). Persisted on the `workflow_run_steps` row as a
/// JSON array and rendered by the per-run outcome card (T-2).
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub struct DeliveryReceipt {
    /// The Composio action slug that produced this side effect
    /// (e.g. `GMAIL_SEND_EMAIL`, `SLACK_SEND_MESSAGE`).
    pub tool: String,
    /// Coarse-grained classification — drives the UI icon + verb
    /// rendering ("📧 Sent email" / "💬 Posted message" / ...).
    pub side_effect_kind: SideEffectKind,
    /// Human-readable target (e.g. recipient email, Slack channel
    /// name, file path). Best-effort extracted from the request
    /// arguments at dispatch time. `None` only if extraction failed
    /// or the tool has no clear "to whom" notion.
    pub recipient: Option<String>,
    /// Provider-side stable id (Gmail message id, Slack ts, Notion
    /// page id). Lets the user link back to the artifact.
    /// `None` when the provider doesn't return one.
    pub message_id: Option<String>,
    /// Deep link to view the artifact in the provider's UI
    /// (`https://mail.google.com/mail/u/0/#sent/<id>`, etc.).
    /// `None` when no canonical link is derivable.
    pub link: Option<String>,
    /// Captured at receipt time so the UI can sort + render
    /// "Sent 3 minutes ago".
    pub at: DateTime<Utc>,
}

/// Coarse classification of the side effect. The catalog is curated
/// — unknown tools fall through to `Other { verb }` rather than
/// hallucinating an icon. Extend this enum (and the matching frontend
/// renderer) when new write-toolkits are added.
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
#[serde(tag = "kind", rename_all = "snake_case")]
pub enum SideEffectKind {
    EmailSent,
    MessagePosted { provider: String }, // slack, discord, telegram, ...
    FileCreated { provider: String },   // gdrive, notion, ...
    RecordCreated { provider: String }, // attio, airtable, notion db
    RecordUpdated { provider: String },
    CalendarEventCreated,
    /// Catch-all for write tools that don't fit a curated category.
    /// `verb` is rendered verbatim in the UI ("Performed X").
    Other { verb: String },
}
```

`RunStep` gets a new field:

```rust
pub struct RunStep {
    // ... existing fields ...
    /// Concrete delivery receipts produced during this step. Empty
    /// for read-only steps or steps that failed before any write.
    #[serde(default)]
    pub delivery_receipts: Vec<DeliveryReceipt>,
}
```

## Implementation outline

### 1. Emit receipts from `composio_execute`

`src/openhuman/composio/tools.rs::ComposioExecuteTool::execute` — in the `Ok(resp)` arm, when `resp.successful == true`, classify the action slug via a new `delivery_receipt::classify(tool, arguments, &resp)` helper and publish a new `DomainEvent::DeliveryReceiptObserved` scoped to the active `session_id`. Mirror the F-16 ToolExecutionCompleted publish pattern at line 1319-1327.

Classification rules (start simple, extend as needed):

| Slug pattern | `SideEffectKind` | recipient extracted from | message_id from | link template |
|---|---|---|---|---|
| `GMAIL_SEND_EMAIL` | `EmailSent` | `arguments.recipient_email` | `resp.data.id` | `https://mail.google.com/mail/u/0/#sent/{id}` |
| `SLACK_SEND_MESSAGE`, `SLACK_CHAT_POSTMESSAGE` | `MessagePosted { "slack" }` | `arguments.channel` (resolved name if available) | `resp.data.ts` | `https://app.slack.com/client/{team}/{channel}/p{ts}` |
| `GOOGLECALENDAR_CREATE_EVENT` | `CalendarEventCreated` | `arguments.summary` | `resp.data.id` | `resp.data.htmlLink` |
| `NOTION_CREATE_PAGE` | `FileCreated { "notion" }` | `arguments.title` | `resp.data.id` | `resp.data.url` |
| `ATTIO_CREATE_RECORD` | `RecordCreated { "attio" }` | `arguments.values.name` | `resp.data.id` | derived from workspace + record type |
| `*_SEND_*` / `*_CREATE_*` / `*_UPDATE_*` / `*_POST_*` (no curated rule) | `Other { verb: "Sent / Created / Updated / Posted" }` | best-effort | best-effort | None |
| Anything else | **no receipt emitted** (it's a read, not a side effect) |

Put this in a new module `src/openhuman/composio/delivery_receipt.rs` with one function per classification rule and a fall-through. Unit-test each rule against real Composio response shapes.

### 2. Subscribe + record in the workflow executor

`src/openhuman/workflows/executor.rs::run_agent_prompt` — already subscribes to `ToolExecutionCompleted` via `subscribe_tool_call_recorder` (line 2966). Extend the same subscriber to also observe `DeliveryReceiptObserved` events scoped to the same `session_id`, accumulating into a `Vec<DeliveryReceipt>`. Thread the vec into `NodeOutput`:

```rust
pub struct NodeOutput {
    pub text: String,
    pub tool_failure_count: u32,
    pub tool_calls: Vec<ToolCallObservation>,
    pub delivery_receipts: Vec<DeliveryReceipt>, // NEW
}
```

The caller in `execute_agent_prompt_node` (line ~2720) writes the receipts into the `RunStep` row.

### 3. Persist

`src/openhuman/workflows/store.rs` — add migration `006_add_delivery_receipts.sql`:

```sql
ALTER TABLE workflow_run_steps
  ADD COLUMN delivery_receipts_json TEXT NOT NULL DEFAULT '[]';
```

Round-trip: store as `serde_json::to_string(&Vec<DeliveryReceipt>)`, read back via `serde_json::from_str` with `unwrap_or_default()` for forward-compat with rows missing the column.

### 4. Expose via RPC

`src/openhuman/workflows/schemas.rs` — extend the `workflows_get_run` response shape so the frontend can read `step.delivery_receipts`. No new RPC; existing one carries it.

## Open Questions (resolve before starting)

1. **OQ-T1-A: extraction failure semantics.** If `classify(GMAIL_SEND_EMAIL, args, resp)` can't find `arguments.recipient_email` (malformed dispatch, schema drift), should we (a) skip the receipt, (b) emit with `recipient: None`, or (c) emit with `recipient: Some("<unknown>")`?
   - *Lean:* (b) — emit the receipt with `recipient: None` so the user sees that something was sent but the system can't say to whom. Skipping (a) hides the side effect; (c) lies.

2. **OQ-T1-B: should receipts be emitted for `_DELETE_*` actions?** These ARE side effects but rendering "✅ Deleted message" feels different from "✅ Sent message".
   - *Lean:* yes, emit as `Other { verb: "Deleted" }`. Phase 2.5 doesn't get a special `Deleted` variant — that can land later if usage shows it matters.

3. **OQ-T1-C: receipts from non-Composio tools?** `channel_send` / `webview_account_send` (Phase 2 stubs) and future native sends.
   - *Lean:* design `DomainEvent::DeliveryReceiptObserved` so any tool can publish, not just composio_execute. Phase 2.5 only wires Composio (broadest coverage); native sends opt in by publishing.

# T-4 Primer: Failure-Mode Catalog

**Project:** OpenHuman — Workflows & Automations / Phase 2.5 Trust UX
**Dependencies:** T-1 + T-2 shipped. Light dependency on T-3 (shares the fix-hint pattern).

---

## What Is This Ticket?

Classify every `RunStatus::Failed` terminal state into a stable structured `FailureReason` enum, persist it on the run row, and render it in T-2's outcome card as a plain-English one-liner plus an optional fix-it action. Closes the loop on "what does this opaque error mean?"

### Why It Matters

Today a failed run gives the user an `error` string like:

> `node \`n1\` failed: agent_prompt step failed: OpenHuman API error (400 Bad Request): {"success":false,"error":"Model 'claude-opus-4-7' is not available. Use GET /openai/v1/models to list available models."}`

That's useful for a developer with grep access. It's useless to a non-technical user. T-4 maps these strings to a small, stable catalog of failure reasons with human explanations:

| Raw signal | `FailureReason` | User-facing one-liner | Suggested fix |
|---|---|---|---|
| Status flipped by F-21's zero-tool-calls guard | `AgentNarratedWithoutActing { narrative_chars }` | "The agent described what it would do but never actually acted. Common with reasoning-class models." | "Try changing the workflow's model to `agentic-v1`." |
| `composio_execute` returned `ToolResult::error` with kind `upstream_provider_error` | `ComposioUpstreamRejected { tool, detail }` | "Composio sent the request to the provider, but the provider rejected it." | "Open the agent's notes for the provider's specific reason. Common fixes: parameter rename, missing field, recipient not found." |
| `OpenHuman API error: Model 'X' is not available` | `ModelUnavailable { model_tried, valid_tiers }` | "The model `X` isn't available in your account." | "Edit the workflow → change `model_tier` to one of: reasoning-v1, agentic-v1, chat-v1, coding-v1." |
| Anthropic / OpenAI 401 | `LlmAuthFailed { provider }` | "Your `{provider}` API key was rejected. It may have been rotated or revoked." | "Update your API key in Settings → Providers." |
| Composio returns `auth_failed` kind | `ConnectionExpired { provider }` | "Your `{provider}` connection has expired or been revoked." | "Reconnect `{provider}` in Settings → Integrations." [Reconnect →] |
| `composio_execute` returned `ToolResult::error` with kind `invalid_slug_shape` | `ToolSlugInvalid { slug }` | "The agent tried to call `{slug}` but that's not a valid action name." | "Usually means a model hallucination. Retry; if it recurs, file a bug." |
| Anything else | `Unknown { raw_detail }` | "The run failed for an unrecognized reason." | (no fix hint; surface raw_detail to user) |

The catalog is **deliberately small** (7 variants) and **stable** — each variant is a stable contract the UI renders against. New failure modes added later mean a new variant + a new renderer entry. The classifier records `tool_error_drift` telemetry (already exists, see `composio/tool_errors.rs:226` for the pattern) when it hits Unknown so we notice when raw signals shift upstream and can extend the catalog.

## Goal

```rust
// src/openhuman/workflows/types.rs

#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
#[serde(tag = "kind", rename_all = "snake_case")]
pub enum FailureReason {
    AgentNarratedWithoutActing { narrative_chars: u32 },
    ComposioUpstreamRejected { tool: String, detail: String },
    ModelUnavailable { model_tried: String, valid_tiers: Vec<String> },
    LlmAuthFailed { provider: String },
    ConnectionExpired { provider: String },
    ToolSlugInvalid { slug: String },
    Unknown { raw_detail: String },
}

pub struct Run {
    // ... existing fields ...
    /// Set when status == Failed. None for Succeeded / Cancelled.
    /// Drives T-2's outcome card failure rendering.
    #[serde(default)]
    pub failure_reason: Option<FailureReason>,
}
```

## Implementation outline

### 1. Classifier

`workflows/failure_classifier.rs` — pattern-match the executor's terminal `error` string against the known signals from F-16 + F-21 + composio + inference layers. Mirror the structure of `composio/tool_errors.rs::classify_composio_error` (string-pattern heuristics with a fall-through `Unknown` that records drift telemetry).

Decision flow:

1. If `error` contains "agent narrated next-action intent" (F-21 signature) → `AgentNarratedWithoutActing { narrative_chars: narrative.chars().count() }`
2. If `error` matches `Model '(.*)' is not available` → `ModelUnavailable { model_tried, valid_tiers: KNOWN_TIERS }`
3. If `error` contains `Invalid Anthropic API Key` → `LlmAuthFailed { provider: "anthropic" }`
4. If `error` contains `Invalid OpenAI API Key` → `LlmAuthFailed { provider: "openai" }`
5. If `error` contains `[composio:error:upstream_provider]` → extract tool slug + detail from the bracket-prefixed message → `ComposioUpstreamRejected { tool, detail }`
6. If `error` contains `kind: auth_failed` (from F-19/F-20 render) → extract provider → `ConnectionExpired { provider }`
7. If `error` contains `kind: invalid_slug_shape` → extract slug → `ToolSlugInvalid { slug }`
8. Else → `Unknown { raw_detail: error.to_string() }` + emit drift telemetry

### 2. Wire into the executor

`workflows/executor.rs::execute_agent_prompt_node` (the same area F-21 modified) — after the terminal status is computed, if status is Failed, call `classify_failure(...)` and pass the result through to the run row write. Update `store::update_run_terminal_with_failure_reason(...)` (extends today's `update_run_terminal`).

Migration `007_add_run_failure_reason.sql`:

```sql
ALTER TABLE workflow_runs
  ADD COLUMN failure_reason_json TEXT;
```

JSON because `FailureReason` is an enum-with-payload. Forward-compat: missing column → `failure_reason: None`.

### 3. Render in the outcome card

`app/src/components/workflows/RunOutcomeCard.tsx` — when status is Failed and `failure_reason` is present, render the "Why this run failed" section using the variant's catalog entry:

| Variant | UI verb | Fix-it action |
|---|---|---|
| `AgentNarratedWithoutActing` | "🤖 The agent described what it would do but never acted." | [Try model `agentic-v1`] (if not already that) |
| `ComposioUpstreamRejected` | "⚠️ `{provider}` rejected the action: `{detail}`" | (none — usually parameter-correction; surfaces detail verbatim) |
| `ModelUnavailable` | "🚫 Model `{model_tried}` not available in your account." | [Edit workflow — try `agentic-v1`] |
| `LlmAuthFailed` | "🔑 Your `{provider}` API key was rejected." | [Open Settings → Providers] |
| `ConnectionExpired` | "🔌 `{provider}` connection expired." | [Reconnect →] (deep link to `/connections`) |
| `ToolSlugInvalid` | "🤖 The agent tried to use an invalid tool name (`{slug}`)." | (none — retry hint only) |
| `Unknown` | "❓ Unrecognized failure." | (none — show raw_detail collapsed) |

i18n keys land in `workflows.failure.*`. Same chunk-file discipline as T-2.

### 4. Drift telemetry

Extend the existing `core/observability.rs::record_classifier_drift` to support a `Workflows` source (today only `Mcp` and `Composio` exist). When `classify_failure` returns `Unknown`, tick the counter + emit a `tracing::warn!(target: "failure_classifier_drift", ...)` event for sentry capture.

## Open Questions

1. **OQ-T4-A: should `ModelUnavailable` carry the *valid* tier list dynamically?**
   - *Lean:* yes — fetch from `inference::provider::factory::is_known_openhuman_tier`'s underlying registry at classification time. Hard-coding the list will drift.

2. **OQ-T4-B: do we backfill `failure_reason` for existing Failed runs?**
   - *Lean:* no. Forward-only. Old rows have `failure_reason: None` and the UI shows the legacy `error` string. Backfilling adds risk for ~10 Failed rows in the user's DB. Not worth it.

3. **OQ-T4-C: should `Unknown` runs auto-open a GitHub issue draft?**
   - *Lean:* no for Phase 2.5. Tempting but out of scope. Phase 6 (proactive agent) might pick this up.

# T-3 Primer: Pre-flight Validation on Save & Enable

**Project:** OpenHuman — Workflows & Automations / Phase 2.5 Trust UX
**Dependencies:** T-1 + T-2 shipped (so failed pre-flight surfaces visually via the same outcome card pattern).

---

## What Is This Ticket?

Add a synchronous **pre-flight validation pipeline** that runs when the user clicks **Save & Enable** on a workflow proposal. The pipeline probes every component the workflow will need at runtime (model, tools, connections, scopes) and **blocks enabling** with a specific actionable error if any layer is broken. Replaces the current "Save & Enable → first run hits 400 → user finds out hours later via cron" failure mode.

### Why It Matters

The 2026-06-07 13:41 failure is the canonical example: user created a workflow, saved + enabled, hit Run → got `400 Bad Request: Model 'claude-opus-4-7' is not available`. The model registration mismatch was knowable at *Save time* (the backend's model list is fetchable), but nothing checked it.

Pre-flight catches the entire class of "I configured X but X doesn't actually exist in this environment" errors before they bite. Every workflow that survives Save & Enable should be **provably runnable**.

---

## Goal

A new domain module `src/openhuman/workflows/preflight.rs` exposing a single async fn:

```rust
pub async fn run_preflight(
    config: &Config,
    proposal: &WorkflowProposal,
) -> PreflightReport;

pub struct PreflightReport {
    pub passed: bool,
    pub checks: Vec<PreflightCheck>,
}

pub struct PreflightCheck {
    pub kind: PreflightCheckKind,
    pub status: PreflightStatus,
    pub detail: String,
    /// Optional fix-it hint surfaced to the user verbatim
    /// (e.g. "Try changing model_tier to `agentic-v1`").
    pub fix_hint: Option<String>,
}

pub enum PreflightCheckKind {
    /// Resolves model_tier (or hint) against the backend's
    /// `/openai/v1/models` registry.
    ModelAvailable,
    /// Probes every `ConnectionRef` in `allowed_connections` against
    /// the live ConnectionsSnapshot; checks status is `Connected`.
    ConnectionLive { connection: ConnectionRef },
    /// For each Composio toolkit in `allowed_connections`, dispatches
    /// a no-op probe (e.g. `*_LIST_*` with `limit=1`) to confirm the
    /// auth token still works at the provider — catches the
    /// `auth_failed` / token-expired case before the first real run.
    ConnectionAuthProbe { connection: ConnectionRef },
    /// Validates the agent_prompt's tools-needed inference: parses
    /// the prompt for action verbs ("send Slack DM" → needs
    /// SLACK_SEND_MESSAGE) and confirms the resolved slug exists in
    /// the toolkit's catalog. Best-effort — partial coverage is fine.
    ToolSlugResolvable { toolkit: String, tool: String },
}

pub enum PreflightStatus { Pass, Warn, Fail }
```

The frontend calls `workflows_preflight(proposal)` synchronously when the user clicks Save & Enable; if any `Fail` status is returned, **the Save is blocked** and the failures render via the same outcome-card pattern T-2 introduced (but in the pre-save modal, not the run-detail view).

## Implementation outline

### 1. Model availability check

`preflight.rs::check_model_available` — call the OpenHuman backend's `GET /openai/v1/models` endpoint and confirm the resolved model tier (after the hint → tier transform in `inference/provider/factory.rs:436-459`) is in the returned list.

- If the proposal has `model_tier: Some("agentic-v1")` and the backend lists it → Pass
- If `model_tier: Some("claude-opus-4-7")` (a stale slug) → Fail with `fix_hint = "Replace with one of: reasoning-v1, agentic-v1, chat-v1, coding-v1"`
- If `model_tier: None` (use the workflow_node default) → Pass (the default is the known-good `agentic-v1` from the user's pin)

### 2. Connection live check

`preflight.rs::check_connection_live` — for each `ConnectionRef` in `proposal.nodes[*].config.allowed_connections`, call into the `connections::aggregator::get_snapshot()` and confirm the matching `ConnectionView` has `status == Connected`.

Reuses F-3's existing snapshot machinery; just an inline read.

### 3. Connection auth probe (Composio-specific)

`preflight.rs::probe_composio_connection_auth` — for each `ConnectionRef::Composio { toolkit_id, .. }`, pick the canonical "cheap read" probe for that toolkit:

| Toolkit | Probe action | Cost |
|---|---|---|
| gmail | `GMAIL_LIST_LABELS` | ~$0.0008 |
| slack | `SLACK_TEAM_INFO` | ~$0.0008 |
| googlecalendar | `GOOGLECALENDAR_CALENDARS_LIST` | ~$0.0008 |
| linear | `LINEAR_LIST_TEAMS` | ~$0.0008 |
| notion | `NOTION_LIST_USERS` | ~$0.0008 |
| attio | `ATTIO_LIST_WORKSPACES` | ~$0.0008 |
| *fallback* | skip auth probe; mark Warn with detail "no curated probe for `{toolkit}`" | 0 |

If the probe returns `auth_failed` → Fail with `fix_hint = "Reconnect {toolkit} in Settings → Integrations"`.

Total pre-flight cost upper bound: ~$0.005 per Save & Enable (6 toolkits × $0.0008). Acceptable.

### 4. Tool-slug resolvability (best-effort)

`preflight.rs::infer_required_tools` — parse the user's prompt for action verbs (`send`, `post`, `create`, `update`, `notify`) + provider mentions (`Slack`, `email`, `calendar`, ...). Map to candidate slugs (`SLACK_SEND_MESSAGE`, `GMAIL_SEND_EMAIL`, `GOOGLECALENDAR_CREATE_EVENT`). For each candidate, confirm the slug is in the toolkit's tool catalog via `composio_list_tools(toolkit)`.

This is best-effort — false-negatives are OK (Warn rather than Fail) because the prompt parser is heuristic. False-positives (claiming a slug doesn't exist when it does) would be worse, so err on the side of Warn over Fail when the parser is uncertain.

### 5. RPC + UI

`src/openhuman/workflows/rpc.rs` — new method `workflows_preflight(proposal: WorkflowProposal) -> RpcOutcome<PreflightReport>`. Reuses the existing proposal validation machinery for shape-correctness; preflight adds the *live* checks on top.

`app/src/components/workflows/preview/WorkflowProposalPreview.tsx` — when the user clicks [Save & Enable], call `workflows_preflight(proposal)` FIRST. If all Pass, persist + enable as today. If any Fail:

- Render a modal listing the failed checks with fix hints
- Disable the [Save & Enable] button
- Offer [Save as Disabled] as an escape hatch (the workflow saves but stays disabled, so the user can fix the underlying issue and enable later from `/workflows`)

If only Warn-level issues, allow Save & Enable but render a yellow banner on the workflow card noting "Saved with N warning(s) — see run history for details".

## Open Questions

1. **OQ-T3-A: should pre-flight run on Run Now too, not just Save & Enable?**
   - *Lean:* yes, but only the model + connection-live checks (skip the auth-probe which costs $). Catches the case where user enabled the workflow yesterday and the connection died overnight.

2. **OQ-T3-B: cache pre-flight results?** If user saves multiple workflows in a row, re-probing every connection is wasteful.
   - *Lean:* 60-second TTL cache keyed by `(connection_ref, probe_kind)`. Same TTL pattern as `INTEGRATIONS_CACHE`. Refreshes are cheap and the cache prevents thundering-herd on the connections panel.

3. **OQ-T3-C: what if the backend's `/openai/v1/models` endpoint is down?**
   - *Lean:* Warn (not Fail) on the model check, with detail "unable to verify model availability — proceeding with `{tier}`". Don't block the user from saving because of a transient backend hiccup.

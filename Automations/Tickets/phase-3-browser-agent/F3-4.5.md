## What Is This Ticket?

Unblock live `browser_action` runs by replacing the stub `WsTransport` (the F3-1 placeholder) with a real WebSocket client against the CEF debug port, plus a profile-aware session opener.

Today every production `browser_action` run fails at session-open with `"live CDP transport not yet wired in Phase 3.1 (WsTransport stub; F3-5/F3-6 enable it)"` — F3-4's executor surfaces the error cleanly but the agent loop never runs. F3-4.5 closes that gap so the hero use case ("DM my last 20 LinkedIn connections to set up a coffee chat") becomes manually testable end-to-end. F3-5 (live preview) and F3-6 (safety preamble + cost caps) layer on top.

### Why before F3-5/F3-6?

- F3-5's live preview needs frame screenshots from a live session anyway — gated on this.
- F3-6's safety preamble is mostly prompt + audit-logging work, which feels off to build for a stub.
- A standalone WsTransport ticket lets us smoke-test the hero workflow manually before investing in the preview UI or safety layer.

### Why It Matters

Phase 3 is about closing the "no API path" automation gap. Without WsTransport the entire phase is theoretical — the type surface, validator, drafter, and tools all work, but no workflow ever drives a real browser. This is the single seam between "Phase 3 ships" and "Phase 3 is real."

## Architectural Decisions

### Why per-session WebSocket instead of one shared `CdpConn`?

The shell-side `app/src-tauri/src/cdp/` runs ONE WebSocket and routes all scanners through `sessionId` filtering. Sharing makes sense there because the four provider scanners run concurrently and they all live in the same shell process.

Phase 3.1 takes the opposite cut: each `BrowserAction` run gets its own WebSocket. Rationale:
- One workflow run = one CdpSession = one ws connection. Simple, no cross-run interference.
- Each tool call inside a run is sequential (browser_observe → browser_act → browser_extract), so per-session serialization via `Mutex` is enough.
- Tokio handles 5–10 parallel websockets to the same port trivially; the resource cost is negligible compared to the LLM agent loop running on top.
- Phase 3.2 can switch to a shared connection if concrete load surfaces the need — the trait surface doesn't change.

### Why `flatten: true` on attach?

Standard CDP idiom — flattens nested session ids into a single message stream. Mirrors the shell-side pattern and is what every Chrome DevTools client does today.

### Why no Drop-time async close?

Same reason as the rest of F3-1: `Drop` can't `.await`. Explicit `session.close().await` is the supported teardown path. The registry's `release(user_id, run_id)` already drops the `Arc<CdpSession>` and triggers the synchronous Drop logging; the underlying WebSocket teardown happens when the transport's Drop runs (tokio-tungstenite closes the socket cleanly on Drop).

### Why no schema-validation of CDP responses?

CDP is a stable protocol with `chromiumdash.appspot.com` documentation; checking the response shape per call is dead weight. Failures show up as missing fields when callers parse the result. The shell-side reference doesn't validate either.
